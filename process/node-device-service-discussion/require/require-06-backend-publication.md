# 后端详细审查：后续公网发布边界

## 范围与已确认条件

用户已确认先交付节点、网关组、设备和服务管理，公网发布另一个阶段。本文件 Q51–Q60 为该后续阶段记录决策问题及答复，不阻塞首阶段建表/API讨论，不要求现在回答连接逻辑，不自动增加功能。明确区分用户决定、后置事项及未采纳建议。

分组进度：第 17–19 组均已回复。每服务手动指定一个入口、公网端口手填，只配置 EasyTier TCP/UDP，自身规则冲突不自动覆盖；地址方案仍留到公网实施前确定。第 19 组补充明确：配置写入/删除成功就是本次操作成功，不等运行时或外网验证；删除服务直接删除对应转发配置。保存结果与已有应用反馈分别展示，公网由用户验证，离线开启仍拒绝并由用户恢复后重试。本轮不再要求用户选择严格运行切换顺序或待撤销状态机。

继续遵守：多台有公网的服务器可以作为候选；服务挂设备；不改现有 config-server 使用方式；不新增复杂心跳或探测定时任务。普通资产登记值、已有实例运行值、配置期望值分别表达。

|Q51|单个服务怎样选择公网入口？|**已确认：**每个服务只选一个入口节点，由用户手动指定。多台服务器可供选择，不设自动默认选择、同时多入口发布或负载均衡；入口调整按 Q59 的配置操作成功标准处理，不强制验证运行时新旧切换|

|Q53|公网映射端口由谁确定，冲突时怎样处理？|**已确认：**用户手填公网端口；冲突时提示，由用户修改后重试，不自动分配或替换。已知配置冲突按实际主机、协议及重叠监听地址处理，不能按 EasyTier 实例各自认作空闲；已有接口返回的占用错误如实反馈。不新增外部进程探测或运行时确认来阻止 Q59 的配置操作成功，也不把配置成功显示为监听已验证|
|Q54|开启公开时，平台自动配置到哪一层？|**已确认：**只配置 EasyTier 转发，主机防火墙、云安全组和 DNS 由用户处理。不增加这些外部系统的自动适配、凭据管理或配置任务；平台无法以 EasyTier 应用成功证明这些前置条件已满足|
|Q55|怎样展示配置保存、应用结果及公网访问？|**已确认并结合 Q59 收敛：**分别展示配置保存结果和已有下发/应用反馈，公网由用户自行验证。配置写入/删除成功即本次操作成功；缺少应用反馈时显示未确认，不阻塞成功或伪称已应用。不增加手动公网检测按钮、定时探测或运行确认协议|
|Q56|公网节点离线时开启公开，拒绝开启还是保存待应用意图？|**已确认：**拒绝开启，节点恢复在线后由用户手动重试。不新建离线待发布意图、自动重试或定时任务；沿用可获得的节点状态判断，不为此增加复杂心跳。此规则针对开启，不扩大为离线禁止删除配置|
|Q57|入口离线时，关闭公开、删除服务/设备与转发规则怎样处理？|**用户自由答复：**“公开不做强绑定 删除了服务时 直接把该条转发规则删除”。关闭公开/删除服务直接删除对应的本功能转发配置；删除设备覆盖其级联服务的配置。不等待入口运行时确认撤销，不因离线强制保留业务记录、待撤销流程或端口占用。配置侧占用随规则删除更新，不宣称运行进程已停止；配置操作自身失败仍需反馈，不能隐藏为全部成功|
|Q58|是否接管现有手工转发，手动修改冲突怎样处理？|**已确认：**只管理本功能创建的规则；遇到手工规则占用或自身规则被手动修改造成冲突时提示，不自动覆盖。不增加旧规则认领功能，新增/修改/撤销只能影响自身有明确归属的规则；当前代码尚无该业务归属机制，需要后续设计|
|Q59|入口更换以什么结果作为成功标准？|**用户自由答复：**“你不用强校验 写入/删除转发配置 成功就是成功”。按必要配置写入/删除结果判断操作成功，不强制等待旧入口停止、新入口监听或公网可达。配置操作顺序与失败反馈由后端设计，不承诺运行时无中断/无重叠，也不新增自动故障切换、双入口过渡状态机或补偿任务；实际写入/删除失败或部分失败必须如实反馈|
|Q60|公网第一版支持到端口转发，还是增加 HTTP/HTTPS 路由及证书管理？|**已确认：**先做 TCP/UDP 端口转发，不增加 HTTP 域名/路径分流或证书管理。TCP 可以透传已有 HTTPS 流量；服务访问链接仍只是展示/跳转资料，不能把 URL 路径作为转发目标或反向代理路由|

## 后端自行负责的要求

- 保留准确定位本功能转发规则所需的最小关联，更新和删除只影响对应项；不把业务记录与入口运行状态强绑定，不借此引入必须等待撤销确认的流程。删除设备时覆盖其全部级联服务对应规则。
- 保护手工规则和配置中的其他字段，识别自身规则被手工修改造成的冲突并提示，不通过覆盖或重新导入绕过 Q58。防火墙、云安全组、DNS、HTTP 路由和证书管理均不在本次公网第一版范围内。
- 单服务按已确认规则手动选择一个入口、填写公网端口；最终配置冲突模型结合尚未确定的地址方案设计，不能静默改端口。不同协议可分别占用同一个数字端口，双协议服务分别校验，必要配置操作都成功才返回整体成功；不新增运行确认门槛。
- 托管实例沿中央配置路径更新；不能为绕过冲突而修改 config-server 协议或直接操作其运行副本。
- 地址、协议和端口在业务 API 层显式校验；转换产生的丢项、未知协议回落不能当作成功。
- 内核 IP、IPv6 的结构化解析与显示由后端正确处理，不要求用户手工拼接脆弱的地址字符串。
- 配置操作成功与应用反馈分开展示；未获得应用/访问证据时不声称已应用/公网可用，也不因缺少这些证据把已成功的配置操作判为失败。公网验证交用户自行进行，不新增强制发布状态机或定时探测。
- 配置写入/删除自身失败须明确反馈；事务、重复删除和部分失败处理由后端结合现有持久化路径设计，不用“无强校验”取消权限、输入、唯一性或 Q58 手工规则保护，也不默认增加后台补偿和等待恢复机制。
- 本轮没有实施上述要求；该清单不能当作已具备功能或测试结果。

## 本轮讨论结束后的边界

Q51–Q60 均已获得本轮答复，其中 Q52 明确后置，不再追问地址细节。先前建议的“确认运行撤销后才能删除或释放端口”“确认新入口应用后再切换”未被采纳，不能在计划中作为必做项。公网实施前仍需结合代码确定入口与服务目标地址、配置定位及错误契约；本轮答复不代表已实现这些能力，也不改变首阶段只做资料管理的范围。
