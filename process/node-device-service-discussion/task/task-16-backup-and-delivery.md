# T16：手工备份、升级恢复与交付

本任务已随实例绑定版本完成：当前云环境11221已手工备份并升级，原TCP22030/账号/节点属性/客户端保持；真实旧库与旧制品恢复演练通过。具体新旧制品、数据核对、备份和部署过程统一记录在[新轮交付记录](../../node-instance-binding-planned/task/release-record.md)，不维护两套相互冲突的部署记录。下面保留原工作顺序与验收边界。

## 写入范围与前置

文档交付为本需求 `task/release-runbook.md`、实际执行后的 `task/release-record.md` 和 test-report。具体部署配置路径必须执行时从现有运行环境读取，不能臆造 `/opt`、Docker compose 或 systemd 服务。运行部署需要届时用户已有授权；先准备可审阅制品、备份步骤和恢复方案，再处理最后发布步骤，不逐项请求批准。

## 工作顺序

1. 接收 T15 的明确版本、验收范围和缺陷结论，定位实际后端启动参数、数据库路径、配置、前端/嵌入制品及当前运行版本；不打印密码、cookie 或 OIDC token。
2. 记录旧制品与配置恢复入口。`Db::new` 启动会自动迁移，故升级前完成一致性 SQLite 备份；停机后备份或使用合适的 SQLite 一致性机制，不能把运行中的数据库文件随意复制当可靠备份。
3. 备份数据、运行配置及必要的 SQLite 附属状态，检查恢复路径与访问权限；测试恢复只在独立副本进行，避免覆盖现网。该实际验证需要测试授权，不能在纯文档阶段执行。
4. 短暂停机替换本次已验证制品、启动执行迁移，记录开始/结束和错误；保留旧账号、节点、来源 IP/地点/型号及配置。没有新增定时备份或健康检测任务。
5. 在获准的部署验收范围内确认登录、节点详情、原实例设置与客户端连接、数据查询和角色能力；错误不能靠清库重建处理。
6. 若恢复旧版，按已验证方案恢复对应旧数据库/配置及旧制品；仅回退二进制不等于兼容已经升级的 schema，不承诺 down migration 无损可用。
7. 输出实际访问地址、代码/制品版本、迁移和备份位置、已知限制与截图链接；涉及远程提交/发布时只执行届时授权的动作，不提前触发 CI。

## 验收条件与边界

新旧版本边界和恢复材料明确，备份能覆盖原有及新增资产数据，保留当前用户/节点/客户端使用方式。新账号类型预置与既有账号初始化不丢数据、不重复恢复已删类型。操作记录如实标注未执行项；无部署证据时不能写“已上线”。

EasyADB/智能家居接入、服务公网发布、Navloom 导航和新节点 deploy 安装不随此次交付暗中上线；公网标记只是资料字段。完成后更新看板和交付记录，不将后置功能算成本轮欠缺验收。
