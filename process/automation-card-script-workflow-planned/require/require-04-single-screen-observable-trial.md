## A. 产品交互目标

### A1 单画面、连续拾取
- 自动化中心卡片唯一 WebRTC 主视频 `PhoneCard.vue` 持续显示，`UiInspectorDialog.vue` 原独立 `<video>` 不再同时展示。
- 控件树、属性、定位候选与动作录入作为右侧停靠面板（窄屏变抽屉）；点击/长按只在原视频有效像素上拾取并高亮，单向同步右侧树；不额外建立第二条 WebRTC。
- 确认录入只追加一个步骤并收起编辑区域；拾取模式留在原卡片，连续右键添加步骤 2/3/4；更新旧步只替换目标、保持 step_id 和其它参数。
- 账号/设备/会话/快照时间、屏幕旋转/宽高发生变化时旧高亮与旧候选失效；全屏侧板与可见图层必须置于正确 top-layer。
- 脚本库中独立只读控件树检查不强制打开卡片投屏，保留无视频工作模式。

### A2 试跑界面去掉重复「定位风险确认」
- 删除常态「手机匹配：1080 × 2340／需要确认定位风险」整块卡片与第二个风险复选框；不再显示“我已核对当前手机的页面、定位和坐标风险”。
- 设备与控件定位仍自动预检：owner 授权、fingerprint、ADB、UiAutomator 状态、快照时效、坐标参考宽高完全一致、selector 唯一性；**硬不兼容必须阻断，不允许通过复选框绕过**。
- 对没有足够只读证据的 selector 或发生歧义/旧树，给单条可处理错误和「刷新控件树／重新拾取」动作，而不是反复要求用户勾选多项风险。
- 保留单个明确的真实执行确认按钮 `确认执行此步骤`；已知会改变设备状态或保存截图证据的步骤须保持必要的知情确认，防止“简化 UI”变成未经同意的动作发送。
- 结果必须区分「只读定位演示」「动作已发送」「断言成功」「失败」「结果未知」，不知道是否执行时不得自动重放。

### A3 试跑期间不断原画面
- 点击「自动准备试跑设备」后，原卡片视频继续播放；准备进度在侧板/卡片状态条实时展示。
- 执行阶段原画面继续实时播放，叠加 `试跑执行中 · 仅观看`；手机真实点击、滑动、页面变化应可见。
- 试跑控制权由执行器独占，页面上的真实 tap/input/键盘解锁等手动动作必须同时在浏览器、Rust 授权层与执行器侧被拒绝（前端灰按钮不算安全保障）。
- 完成 + 设备 worker 清理确认后恢复手控；`cleanup_pending` 或 `outcome_unknown` 则仍禁止新的动作、允许只读查看与排障。
- 浏览器或 WebRTC 断线不能自动重试手机动作，更不能自动复活已取消运行；多台手机并行独立，不可偷用其他浏览器的控制会话。

## B. 技术经理代码现状及归因

| 组件 | 当前行为 | 对目标的影响 |
|---|---|---|
| `PhoneCard.vue` | 持有真正的主 `<video>`、`usePhoneSession()`、像素映射与拾取开关，暴露 `getStream()` | 可复用唯一视频画面，不需第二条流 |
| `AutomationCenter.vue::openInspector()` | 取得 `card.getStream()` 传给 Inspector | 目前是**同一条 MediaStream、两个 HTML video 元素**，不是两次视频网络连接 |
| `UiInspectorDialog.vue::setVideo()` | `video.srcObject=props.stream`，modal 并在弹窗中显示缩小视频 | 可移除第二个 video，将属性工作台 dock 回原卡片 |
| `CardTrialPanel.vue::prepare()` | 在检查 ADB/UIA 前即调用 `releaseOwnedTrialPreviews()` | **前端主动导致现有画面关闭**，并非 WebRTC 技术上不能与 UIA 同在 |
| `automation-run-handoff.ts` | 关闭本页拥有的 WebRTC session，核对服务端 active_session 和 run_occupied，再移交 | 当前设计为保守的控制权交接；不能单纯跳过检查 |
| `journal.py::claim()` | 根据 endpoint 或 device_id 单行 `controls` 拒绝不同 holder 的并发独占操作 | 是 **EasyTier 项目自己写的互斥策略**，不是 ADB/scrcpy/UiAutomator2/WebRTC 的框架硬限制 |
| `runtime.py::create_session()` / `offer()` | 创建视频流自身**不直接**调用 `claim()` | 只读视频理论上可以不占动作锁，需要核查 Rust active_session 规则 |
| `runtime.py::command()` / `unlock()` | 发送手机动作前 `claim(target, "session:"+sid, "manual")`，此手控 holder 不在每次动作后自动释放 | 开过投屏并手动操作后，手控 holder 常驻；后续 prepare/script 会因独占发生冲突 |
| `runtime.py::prepare()` / `_run_device()` | 分别以 prepare、script holder 获取同一控制权 | 无法与已持有 manual holder 的 session 共存 |
| `media.py` | scrcpy/H.264/WebRTC 媒体具有自身生命周期与单设备 session 限制 | 视频资源与动作控制资源目前绑定较深，需明确观看 lease 及失效/清理策略 |
| `CardTrialPanel.vue` / `automation-device-compatibility.ts` | 许多 selector 或绝对坐标步骤直接产出 `confirm`，同时要求额外 `compatibilityConsent` | 形成用户截图中重复的风险确认，需改成后台自动判定和异常阻断 |

### B1 谁限制的？

这是自研 EasyTier Automation Executor 的 `Journal` 控制权仲裁，相关文件最初可追溯到 2026-10-23 提交 `34c559638d78`；后续仓库变更对其做了恢复、资源排他与清理加固。**不是 Android 或第三方框架的固定限制**。

需要准确区分：视频连接本身未必占有 Journal 的 manual 控制权；第一次真实手控/解锁后会申请 manual 控制权。当前试跑前**无条件主动关闭本页预览**，以便 Rust 和 Executor 都确认释放，属于保守设计，目的是防重复控制，不应无校验地删除。

### B2 不同方案比较

| 方案 | 体验 | 开发难度 | 安全/兼容代价 | 结论 |
|---|---|---|---|---|
| 方案 1：仅跳过前端 close、保持现有结构 | 画面有时不断 | 看似低 | 有 manual claim 的设备 prepare 会 `device_busy`；Rust `active_session` 也可能拒绝 run，且手动控制未被执行器阻断 | **禁止** |
| 方案 2：视频观看与动作控制双权限，保留同一 WebRTC 画面；试跑时降级为只读 | 视频持续、流畅，用户在原卡片看动作 | **高**（前端+Rust+Executor，需跨层测试） | 需要 read-only/viewer lease、操作者授权、脚本写锁、会话停手和屏幕/控制生命周期隔离；跨浏览器与 crash 恢复明确 | **推荐正式方案** |
| 方案 3：执行器提供低帧率只读屏幕快照供正在运行的脚本回看 | 可观察变化，但不够流畅 | 中（新数据源/接口/前端） | 截图频繁 ADB IO，可能与 UIA 并发、隐私与带宽有开销；算不上“实时画面保留” | 应急降级，非默认 |
| 方案 4：执行时另一份 scrcpy/WebRTC 独立预览 | 画面实时但可能闪断 | 中高 | ADB/编码/资源重复，MediaManager 对同设备也阻断，会话数量和互斥更复杂 | 不推荐 |

### B3 推荐的目标控制权模型

```text
phone (device_id / target_fingerprint)
├─ video_lease (只读观察，保留原 WebRTC 流；绑定授权用户与观察者身份)
│  └─ 允许观看像素帧、查询只读状态；禁止触控、输入、解锁、停止运行
└─ action_lease (每台手机最多一个写入者)
   ├─ manual   —— 正常手控
   ├─ prepare  —— 必要时的 ADB/UIA 初始化，防竞态
   └─ script   —— 单步/完整脚本真正执行
```

目标原子交接：
1. `manual → prepare/script` 时，先冻结界面写入口；执行器回收未完成的 touch/input 并确认清理；只释放动作控制权，**不关闭同一视频源**。
2. Rust `active_session` 与 `run_occupied` 的限制改为“只读观看不占执行写锁”，但仍检查 viewer 的 owner、session ID、fingerprint、租期和写权限。
3. 只有控制权正式移交后才由脚本执行器开始动作；等待期间用户只能观看准备进度和视频。
4. 执行完成后严格验证 worker 与控制清理、绑定仍一致、视频源未失效，才能以显式状态恢复手控；失败/未知不能自动解锁或发送动作。
5. 视频断开后允许按观看协议重新建立**只读流**，但不得重放试跑；另一浏览器不得抢走正在执行的 session 控制权。

潜在硬点：scrcpy 同时承载编码、控制通道及 wake/unlock；不能仅以“隐藏按钮”保证 read-only。应在 Executor HTTP/WS command、Rust 设备会话占用、Journal 写入锁中间逐级校验、并验证 Android 控件树抓取与媒体编码同时工作时的性能、延迟和尺寸一致性。

## D. 完成判定（新增验收，不覆盖 AC01–AC12）

- **NEW-01**：手机卡片/控件工作台仅一个视频播放器；连续录入至少四步不跳页面、不重启 WebRTC、不创建第二条媒体会话。
- **NEW-02**：同一手机同一页面正常拾取的安全步骤，单步试跑不出现“需要确认定位风险”大卡/额外复选框；真正不兼容仍不允许执行。
- **NEW-03**：自动准备前、ADB 检查/UIA 准备期间、步骤实际执行及返回结果期间，**同一个卡片实时画面持续展示**，能看到页面变化；如果 Android 编码源本身异常，应诚实显示“视频中断”而非伪装成功。
- **NEW-04**：运行中浏览器手动 tap/text/key/unlock/群控不能透过底层 API；原执行动作正常完成、执行器清理后恢复手控。
- **NEW-05**：一机两页、两用户、跨手机、断线、执行器重启、未知动作和执行器独占锁竞争下，没有双写者、没有自动重试手机动作、没有绕过授权的观看会话。
- **NEW-06**：显示的动作状态与 run_id/device_id/step_id 对齐；定位演示不会创建运行记录，未知状态不会被当成失败后自动再次点击。
- **NEW-07**：真实全屏下可查看侧板/进度、返回原卡片时页面不变形，主视频有效像素映射正确、UIA 高亮与画面位置一致。
