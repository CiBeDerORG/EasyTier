# 需求、计划与任务协作规则

本规则适用于全仓库，由根 [AGENTS.md](../AGENTS.md) 加载。`MUST` 为必须，`SHOULD` 为应遵循且偏离时说明理由。目的在于让人工和多个 Agent 能找到同一份需求、认领独立工作、按依赖联调并留下可核验的结果。

## 1. 固定目录与事实来源

| 产物 | 位置 | 负责的内容 |
| --- | --- | --- |
| 需求分析 | `docs/requirements/<feature>.md`，或 `docs/` 下已有对应分析文档 | 用户任务、现状证据、范围、约束、待决项、需求与验收编号 |
| 实施计划 | `process/plan/<feature>.md` | 方案、契约、依赖、并行批次、集成顺序、迁移与验证策略 |
| 任务看板 | [task/README.md](task/README.md) | 跨任务概览、状态、负责人、依赖和明细链接 |
| 任务明细 | `process/task/<feature>/<task-id>-<purpose>.md` | 单项任务元数据、输入、写入范围、验收、交付证据和阻塞原因 |

- **MUST** 每次需求分析新建或更新 `docs/` 下的对应文档，不仅在聊天中输出结论。同一需求继续分析时更新原文档，避免出现多个互相冲突的“最终版”。
- **MUST** 新建实施计划全部放在 `process/plan/`，任务拆解全部放在 `process/task/`。分析中可以说明产品优先级，但实施批次与执行状态只在计划/任务中维护。
- **MUST** 分析链接计划与看板，计划链接分析与任务，任务链接分析与计划；需求/验收/任务编号保持稳定。命名遵循 [命名规范](../docs/architecture/naming.md)。
- 既有历史文档不批量移动；继续推进其中的需求时，将活动实施计划、任务整理到规定目录，并更新原文档引用，不留下两套活动计划。
- 小型修复可以只有一项任务和简短计划，使用同样目录与必要字段；不要求为纯文案改动制造并行工作或联调流程。

## 2. 从需求到可执行任务

1. **分析**：使用 [需求模板](../docs/requirements/template.md) 或更新已有分析，区分源码事实、建议与待决项，给需求和验收编号；记录用户目标及限制。
2. **计划**：使用 [计划模板](plan/template.md) 明确方案与依赖。对多 Agent 工作，先定义接口、数据结构、错误、状态和兼容行为。
3. **拆分**：使用 [任务模板](task/template.md)，按独立模块/文件/可验证结果拆分，填写输入、输出、依赖与写入范围；建立看板。
4. **认领并执行**：确认依赖已完成或有明确可用的交付契约，指定唯一负责人后开始；只写本任务拥有的范围。
5. **集成与验收**：各任务完成自身验证后交付，再按计划执行后端/前端接线、真实端到端联调、升级与整体验收。

这些步骤是工作记录要求，不增加默认审批流程。已有明确授权和可确定的实施选择应继续推进；确实缺少会影响范围的决定时，记录假设或阻塞点，并推进不依赖它的任务。

## 3. 优先按低耦合边界并行

- **MUST** 优先寻找写入文件不同、职责独立、输入/输出可定义的工作包，而非把同一个大文件分给多个 Agent。任务名称“前端”“后端”不能替代具体写入范围。
- **MUST** 在明细 `write_scope` 中列出允许修改的文件或目录，在计划中指定共享文件的唯一写入者；两个可同时执行的任务不得拥有重叠的写入范围。目录与其子路径也算重叠。
- **MUST** 对路由入口、公共类型、语言资源、模块注册、migration 列表、构建清单、锁文件和看板明确所有权；需要扩展范围时先由协调者调整任务与依赖，再编辑。
- **MUST** 一个任务只能有一个当前负责人。其他 Agent 可只读评审；同文件变更通过串行交接或单一集成者处理。独立 worktree 可减少工作区干扰，但不能消除语义冲突。
- **MUST** 契约变更回写计划并通知消费方；受影响任务暂停依赖部分，不能各自猜测接口。依赖真实实现才能验证的任务不能靠 mock 标记完成。
- **MUST** 保证任务代码参与实际编译与针对性验证；模块声明和最小测试接线由其指定所有者负责，不能到最终联调才首次编译。
- **SHOULD** 先做契约/基础，再并行开展数据库、独立界面和 HTTP 适配；后端策略和业务服务在基础可用后并行，最后汇合联调。具体依赖以项目实际所有权为准。
- **MUST** 保持同一业务事务、状态所有者与兼容性决策完整；存在依赖时明确串行，不以“Agent 数量越多越好”为目标。

## 4. 明细元数据与看板

任务文件顶部使用 YAML front matter，字段见 [任务模板](task/template.md)。`id`、`feature`、`status`、`owner`、`depends_on`、`write_scope`、`requirements`、`acceptance`、`updated_at` 为必填；无负责人用 `null`，无依赖用 `[]`。路径从仓库根开始；未来新增路径明确标注为计划范围。

| 状态 | 含义与进入条件 |
| --- | --- |
| `backlog` | 已记录，范围/契约或排期尚未整理到可执行程度 |
| `ready` | 任务范围明确，依赖满足，可以认领；不表示正在执行 |
| `in_progress` | 已指定负责人并开始工作 |
| `blocked` | 受前置任务或具体问题阻塞，明细记录原因与解除条件 |
| `in_review` | 实现与本项验证已交付，等待评审或指定核验 |
| `done` | 本项验收满足且有实际证据；涉及的整体功能是否完成由联调/验收任务判断 |
| `cancelled` | 已取消，保留编号及原因，不复用编号 |

- **MUST** 任务明细是状态、负责人和依赖的事实源；看板是其摘要，由当前协调者单一维护。每次认领、阻塞、评审、完成或取消时，同步明细和看板，更新日期。
- 执行者向协调者提交状态变化与证据，由协调者在同一次变更中同步，避免多个 Agent 同时写公共看板。尚未同步的状态以明细为准并立即修正摘要。
- **MUST** `blocked` 写明阻塞点、影响范围、解除条件；`in_review`/`done` 写明改动、测试结果和限制，不能只写“已完成”。失败后退回合适状态并保留失败证据。
- **MUST** 文档规划完成与功能实现完成分别表述；生成任务文件不能把其中的开发任务标为 `done`。
- 当前看板为仓库内 Markdown，人工维护；本规则不代表已配置自动同步、任务调度服务或 CI 门禁。

## 5. 联调任务与交接

跨模块功能必须显式安排联调任务，内容至少包括：

- **输入条件**：前置任务、契约版本、可运行构建、数据库与测试账号准备；不得使用真实凭据作为文档样例。
- **负责人和范围**：谁负责接线及验证，谁有权修改公共入口；不默认授权联调者重写所有模块。
- **真实场景**：覆盖成功与失败、权限/会话、持久化、兼容性和升级；适用时验证实际浏览器与服务，不只依靠 mock。
- **失败回派**：将缺陷回派原所有者或新增关联修复任务；同步状态/写入范围，再继续并行。联调记录阻塞，不能掩盖未通过项。
- **退出条件**：关联验收全部有结论，说明通过/失败/未执行及原因，留下可复现命令或人工步骤和剩余限制。

每项任务交付时在明细记录：最终文件、对外接口、实际验证与结果、需集成的内容、剩余问题；协调者据此解除下游依赖。具体命令来自仓库现有脚本与 CI；不得用零测试或未注册模块的构建结果宣称已覆盖功能。
